# 블로그 글 작성 지침

블로그 「기록」(/blog)의 글을 블록 문서로 쓰는 규칙이다. 블록마다 필드는 `block_schema`로 확인한다. 권장 블록 순서는 이 도구가 함께 돌려주는 `skeleton`에 있다.

## 1. 무엇을 쓰나

- 기술 사례 글이 기본이다. 다음 순서로 쓴다: 무엇을 → 왜(제약) → 어떻게(구조·구현) → 무엇에 부딪혔나(문제 → 원인 → 해결) → 남은 한계.
- 사용자가 빼라고 한 목적이나 사례는 쓰지 않는다. 의도를 짐작해 다시 넣지 않는다. 애매하면 「기술 위주로」 쓴다.

## 2. 공개 금지 (가장 중요)

- 실제 IP(사설 IP 포함), 내부 도메인과 호스트 이름, 비밀값, 토큰, 개인 경로(C:\Users\<이름>)를 쓰지 않는다.
- 실제 사람 이름, 계정, 대화 내용을 쓰지 않는다. 스크린샷 속 남의 창과 대화는 흐리게 처리한다. 시연은 「나와의 채팅」처럼 본인만 있는 곳에서 한다.
- 오픈소스를 바탕으로 했으면 원본 저장소와 라이선스를 밝히고 링크한다.

## 3. 구조와 블록

- 첫 블록은 `cover`다. 그다음에 「왜 만들었나」 `markdown`(`level` 2)을 둔다.
- 시연은 본문 앞쪽에 `gallery`로 둔다. 구조는 `steps`(`layout` `horizontal`), 기능 목록은 `table`, 원칙과 경고는 `callout`으로 쓴다.
- 「부딪힌 문제와 해결」은 ### 소제목으로 사례마다 「증상 → 원인 → 해결(→)」 순서로 쓴다.
- 글의 `title`은 「무엇을 했나 — 부제」 형태로 쓴다. `summary`는 1~2문장, `tags`는 3~5개다.
- 숫자(대기 시간, 버전, 건수)는 현재 값으로 맞춘다. 고친 뒤에는 본문 다른 곳에 옛 값이 남았는지 확인한다.

## 4. 이미지

- 이미지가 빈약하면 안 된다. 「도구를 호출하는 모습」과 「그 결과가 실제로 나타난 모습」을 짝으로 보여 준다(호출 → 결과, 화면 → 구조화된 데이터).
- 대표 이미지(`cover_media_id`)는 가로로 길게(예: 2400x950) 만든다. 잘려도 핵심(제목, 로고, 결과 화면)이 보이게 짠다. 세로 캡처를 그대로 대표 이미지로 쓰면 가운데 빈 배경만 남는다.
- 그려서 만든 그림(호출·응답 카드)은 `caption`에 「실제 호출 인자와 응답을 옮긴 것」이라고 밝힌다. 실제 캡처와 구분한다.
- 모든 이미지에 `alt`(무엇이 보이는지)와 `caption`(무엇을 말하는지)을 쓴다.
- 업로드는 `start_upload` → PUT → `complete_upload` 순서다. 쓰지 않게 된 미디어는 정리한다.

## 5. 발행

- 초안(draft)으로 만들고(`create_post`), 사용자 확인을 받은 뒤 `publish_post`한다.
- 초안은 `issue_post_preview_url`로 낸 미리보기 링크로 먼저 보여 준다.
- 발행 뒤 공개 URL이 200인지, 링크가 렌더링되는지 확인한다.
